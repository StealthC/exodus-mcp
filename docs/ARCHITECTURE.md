# Architecture

## Decision

Exodus MCP will be a two-process application:

1. A Go process owns the local Streamable HTTP endpoint and MCP protocol.
2. A native C++ Exodus extension owns all interaction with the running emulator.

They communicate through authenticated local IPC. On Windows, the first
transport will be a named pipe. The native extension must not expose a network
listener or parse public HTTP traffic.

An artifact store is owned by the Go process. It persists bounded metadata and
immutable files outside the MCP response path, then serves authenticated local
downloads over HTTP.

## Why this split

- The HTTP server can be tested without starting Exodus.
- Protocol updates and failures are isolated from the emulator process.
- The C++ extension stays small and uses the Exodus SDK boundary.
- The server can run as a single, conventional local executable.
- The structure preserves a clean `vendor/exodus` submodule and makes upstream
  pin changes observable in code review.

## Concurrency and analysis contexts

An Exodus process represents one mutable emulation state. It cannot safely
execute parallel frame advances, input changes, or memory writes.

The server will therefore expose **analysis contexts** as explicit handles,
for example `context_create` returning `ctx_...`. Context-local data includes
symbols, annotations, artifact references, saved snapshots, and preferences.
Every emulator operation passes through one serialized scheduler.

Read-only operations may be queued concurrently but execute serially against a
consistent emulator point. Mutating operations require an exclusive context
lease. A future multi-instance manager can provide actual parallelism by
launching separate Exodus processes, one bridge per instance.

These handles are application concepts, not MCP protocol sessions. Modern MCP
removed protocol-level HTTP sessions in revision `2026-07-28`.

## Safety boundary

- Bind the HTTP server to loopback by default.
- Validate `Origin` and require authentication before accepting remote binds.
- Use an unguessable IPC capability generated by the server at startup.
- Validate command schemas at both the HTTP and native-bridge boundaries.
- Never run user scripting inside the Exodus process in the first release.
- Use allowlisted directories for ROMs, artifacts, and scripts.

## Large-output boundary

The model context is a scarce resource and is not a binary-analysis data lake.
Any command that can produce substantial output must write an artifact instead
of serializing the full result in a tool response. This includes ROM slices,
memory dumps, register traces, VDP images, disassembly listings, code/data
coverage, and script output.

Each artifact has an opaque ID, immutable bytes, content type, byte count, and
SHA-256. The server exposes a loopback-only HTTP URL that supports byte ranges,
and an MCP resource URI for discovery. Tool results carry a compact summary and
the artifact descriptor. See [Artifact delivery](ARTIFACTS.md).

## Data interpretation boundary

All multi-byte values crossing the native bridge must carry explicit byte-order
and address-space metadata. The bridge must never apply the host machine's
native byte order as an implicit default. The current target-specific baseline
is 68000 `big-endian`, Z80 `little-endian`, and device-specific VDP semantics.
Raw byte slices remain in address order and are not decoded until a caller asks
for an explicitly declared representation.

## First implementation spike

The first native plugin must prove only these capabilities:

1. Exodus discovers and loads the extension.
2. The extension can report its lifecycle and loaded modules over IPC.
3. A read-only request is scheduled safely on the correct emulator thread.
4. Shutdown disconnects cleanly without blocking Exodus.

## Native spike status

`native-plugin/ExodusMcpPlugin` now implements the extension side of this
spike. It is a persistent global extension and deliberately starts no network
listener. When the launcher provides `EXODUS_MCP_PIPE_NAME` and
`EXODUS_MCP_CAPABILITY`, it listens on that named pipe and authorizes only a
small `status` request. The reply contains lifecycle information and the count
of modules observed while the extension initialized.

The Go server now has the named-pipe client used by `bridge_status`. The
remaining work is a launcher that generates and injects the capability, plus
the serialized command scheduler. Do not expose emulator data until that
scheduler dispatches every read safely on the Exodus emulation thread.

No memory mutation, frame advance, ROM loading, or scripting is in scope for
that spike.
